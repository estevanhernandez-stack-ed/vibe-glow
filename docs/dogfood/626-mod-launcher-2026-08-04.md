# Dogfood retro — 626 Mod Launcher (2026-08-04)

First full vibe-glow campaign, run end to end on a WinUI 3 / .NET 10 mod
manager with the winui-powershell adapter. Identity → 46-finding audit →
8 waves → reveal (Forge flagship + default flip, shipped as v0.16.0).
~30 PRs, every wave through a fresh-reviewer gate plus a post-merge
re-review. This file is input to the first hardening pass.

## What the audit missed

- **A token can be "wired" and still dead.** The audit correctly filed
  accent_bloom as unconsumed (F-002), but nothing in the audit stage asks
  "does the *platform* have a consumer mechanism at all?" WinUI has no CSS
  box-shadow; the fix needed a hand-rolled composition DropShadow service.
  Audit findings that imply a *new mechanism* (not a re-style) deserve a
  cost flag at audit time — F-002 sat open for six waves partly because it
  was priced like a re-style.
- **Declaration order vs layout order.** The audit measured the mod row's
  visual anatomy (F-005) but never checked tab/UIA order. The wave-8 column
  swap initially shipped with the toggle still declared fifth — keyboard
  users got the new geometry with the old focus order. An a11y-order lint
  (declaration order ≈ column order) belongs in the audit's accessibility
  sweep.
- **Persistence assumptions.** Nobody — audit included — noticed the theme
  choice isn't persisted until the reveal's default flip made it matter.
  "What state survives a restart" is a cheap audit question with outsized
  reveal consequences.
- **Comment drift as a finding class.** Twice, a stale comment survived its
  code and asserted the *old* design (fill rationale on an outlined chip;
  cyan on an amber default). Both were caught by reviewers, not the
  register. An audit pass that greps comments near changed surfaces for
  contradicted claims would have caught neither at audit time — this one
  belongs in the wave close-out checklist instead.

## What the waves fought

- **The scoreboard lied.** Waves 6–7 summaries carried forward a "zero
  severity-4+ open" claim that the register rows contradicted; the reveal
  gate caught it and cost a full extra wave (8) before the reveal could
  run. Rule now institutionalized in the register itself: scoreboard lines
  are re-derived from rows, never carried forward. vibe-glow's :reveal
  precondition check (re-derive from the register, not from wave summaries)
  is what saved the campaign — keep it adversarial.
- **WinUI popup timing is hostile to one-shot hooks.** The dialog-shell
  title stretch worked on `Opened` in one run and failed in the next —
  the popup tree wiring races Opened in both directions. The deterministic
  signal is the injected content's own `Loaded`. Lesson for the adapter
  docs: any "fix up the template after ShowAsync" pattern must key off
  content Loaded, and single-run pixel verification of a timing-dependent
  fix is not verification — run it at least twice.
- **Template pins.** Two stock-template behaviors ate wave time: the Title
  ContentControl pinned to HorizontalAlignment=Left (rail wouldn't span),
  and ContentDialog's UIA name deriving only from string Titles (element
  content silently drops the dialog's accessible name). Both are now known
  WinUI patterns worth shipping in the adapter's field notes.
- **Review gates earned their cost every single wave.** The App layer is
  headless-untestable; fresh-eyes reviewers caught claimed-but-not-shipped
  fixes (twice), dead-code copy, focus-order regressions, and a
  12-of-23-values pin test named as a full guard. The two-reviewer shape
  (fresh Opus pre-merge + post-merge re-review; core-purity when Core is
  touched) is the right default for UI campaigns on untestable shells.

## What the adapter couldn't capture

- **States behind interaction.** Hover, drag-in-progress, flyouts-open,
  and the 160ms bloom fade are invisible to the F8 screenshot loop. The
  glow transition shipped verified-by-code, not verified-by-pixel.
- **Narrator/UIA runtime behavior.** AutomationProperties and live-region
  wiring were verified structurally (UIA tree lookups) but actual Narrator
  utterances remain a manual smoke item. An adapter hook that dumps the
  UIA tree with names/roles per capture would close half this gap cheaply.
- **The watcher gap.** Early capture rounds lost frames when the watcher
  wasn't running while the user drove dialogs; the campaign re-captured.
  Single-shot `-Surface` mode + UIA-driven clicks (used from wave 8 on)
  turned out to be the reliable pattern — the agent can open dialogs and
  capture without the user in the loop. Promote UIA-driven capture from
  improvisation to a first-class adapter mode.
- **Pixel sampling beats eyeballing.** The deceptive-downscale problem hit
  twice (a filled button that looked outlined at preview scale; a halo too
  subtle to see). PIL crops + per-pixel sampling settled both. The adapter
  should ship a `sample.py` (crop + walk a gradient) next to capture.ps1.

## Numbers

- 46 audited findings + 3 register corrections; 38 → 46 clean across 8
  waves; refusals stand at the invariant line (token-contract breaks).
- 1544 → 1546 tests; zero Core-purity violations across the campaign.
- 8 waves, ~30 PRs, 2 hotfixes, 1 flagship theme, 1 false scoreboard claim
  caught at the gate.
